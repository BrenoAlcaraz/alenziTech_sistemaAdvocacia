Superuser: is_superuser=True não concede mais acesso administrativo de tenant (bypass removido deliberadamente no commit 452eeb6). Continua controlando acesso ao Django Admin (comportamento nativo do Django, não customizado).
Grupos: administrador_escritorio, limitado, financeiro ativos; gerente/advogado legados (preservados no banco, sem novos usuários possíveis via UI).
Cargos: PerfilUsuario.cargo — texto livre, confirmado sem qualquer papel em autorização (docstring do próprio model confirma, embora a docstring esteja desatualizada em outros pontos, ver Seção 9).
Equipes: Equipe/MembroEquipe — hierarquia com equipe_pai, gerente por eh_gerente. Gestão via configuracoes, protegida por @requer_admin_escritorio.
Gerente de equipe: MembroEquipe.eh_gerente=True é dado organizacional puro — não confere nenhum privilégio de acesso a dados de outros usuários (a função usuario_eh_gerente_de_alguma_equipe existe mas não é chamada em lugar nenhum fora de si mesma).
Desativação de usuário: User.is_active é checado em permissao_efetiva/usuario_admin_escritorio, mas não há UI para desativar um usuário (nenhuma view encontrada com esse propósito).
Redefinição de senha: não implementada (nenhum PasswordChangeForm/PasswordResetView encontrado nas views auditadas).
Convites: não implementados.
9. Arquitetura real de permissões
Esta é a seção mais densa da auditoria — resume o trabalho dos agentes de investigação sobre apps/accounts.

9.1 Grupos ativos vs. legados
Ativos (apps/accounts/decorators.py:7-20): administrador_escritorio, limitado, financeiro.
Legados, preservados no banco sem usuários novos: gerente, advogado (migrados para limitado pela migration 0006, objetos Group nunca excluídos).
Continuam ativamente usados em produção (não são vestígio morto): apps/accounts/forms.py (único mecanismo de atribuição de papel), apps/accounts/permissoes.py::tipo_conta_usuario (fallback sempre ativo quando não há UsuarioPapel), apps/configuracoes/views.py (via obter_papel_principal_usuario).
9.2 Papéis técnicos dinâmicos ("kernel")
PapelAcesso (apps/accounts/models.py:118-182) — nome único, codigo_preset, protegido_sistema. Docstring afirma que a proteção de presets "será aplicada por services e forms em etapas futuras" — não implementado: não há nenhuma view/form de gestão de PapelAcesso.
UsuarioPapel (models.py:185-237) — M2M com atributos entre User e PapelAcesso, múltiplos papéis por usuário, campo atribuido_por (auditoria mínima, nunca populado em produção pois não há UI de atribuição).
5 presets de fábrica criados pela migration 0011_migrar_papeis_e_presets.py: socio_gestor_nucleo, advogado_associado, estagiario_paralegal, gestor_financeiro, secretaria_recepcao. Apenas 2 (advogado_associado, gestor_financeiro) recebem UsuarioPapel reais (migração automática dos grupos limitado/financeiro). Os outros 3 têm matriz de permissão semeada mas zero usuários possíveis — não existe caminho de UI para atribuí-los.
9.3 Permissões e habilitações — modelos, constantes, precedência
PermissaoPapel (models.py:240-342) e PermissaoUsuario (345-416): granularidade de módulo (processos, clientes, financeiro, tarefas, modelos, chat, painel, agenda, gerir), com nível (somente_seus/todos para a maioria; solicitacoes/dados para financeiro; vazio para chat/gerir). Ambos suportam regime híbrido tipo_conta (legado) OU papel (FK, dinâmico) — constraint de banco é OR, não XOR: nada impede uma linha com os dois preenchidos simultaneamente (achado de integridade, não explorado pelos dados atuais).
HabilitacaoPapel/HabilitacaoUsuario (419-636): granularidade de item dentro de um módulo (ex.: processos_criar, gerir_criar_usuario) — 15 itens definidos em apps/accounts/permissoes_constants.py:89-126. Mesma estrutura híbrida, mesmo achado OR-não-XOR.
Constantes: apps/accounts/permissoes_constants.py (199 linhas) — única fonte "canônica" de módulos/níveis/itens, mas duplicada sem referência cruzada em pelo menos três outros lugares: apps/accounts/decorators.py (nomes de grupo), a migration 0011 (catálogo hardcoded, com guard-rails de validação cruzada para se proteger contra drift), e apps/configuracoes/views.py::_MODULOS_CONFIG (matriz hardcoded na view permissoes, sem importar de permissoes_constants.py).
Precedência de resolução (apps/accounts/permissoes.py::permissao_efetiva, confirmada linha a linha): (1) módulo inválido → nega sem query; (2) usuário sem pk → nega; (3) is_active=False → nega; (4) usuario_admin_escritorio → bypass total; (5) PermissaoUsuario individual → prevalece sobre tudo; (6) se existe qualquer UsuarioPapel (mesmo inativo) → resolve exclusivamente pelo caminho dinâmico, nunca cai no fallback de Group; (7) só na ausência total de UsuarioPapel → fallback legado via tipo_conta_usuario + Group. Mesma estrutura em habilitacao_efetiva, com a regra adicional de que habilitação só é checada se a permissão do módulo estiver ativa.
Tratamento do administrador: bypass total, nunca consulta as tabelas de permissão — confirmado consistente entre permissao_efetiva e habilitacao_efetiva.
Tratamento do financeiro: tem níveis próprios (solicitacoes/dados) modelados, mas nenhuma view de apps/financeiro consulta essas permissões — a distinção nunca é aplicada em código.
Tratamento do "limitado": é o tipo de conta padrão para não-admin/não-financeiro; sem diferenciação adicional.
Tratamento do gerente de equipe: MembroEquipe.eh_gerente é inteiramente desconectado do sistema de permissões/habilitações — são dois subsistemas paralelos que nunca se cruzam no código.
Cache: nenhum (cache.get/set — zero ocorrências em apps/accounts). Existe apenas um cache de escopo de uma única chamada (_AupContexto), não entre requisições.
Auditoria: apenas UsuarioPapel.atribuido_por (nunca populado em produção) e timestamps padrão. Não há model de log/histórico de mudança de permissão.
9.4 Decorators e context processors
apps/accounts/decorators.py::requer_admin_escritorio — único decorator de autorização real do projeto, tudo-ou-nada (admin vs. não-admin). Usado extensivamente em apps/configuracoes/views.py.
Não existe nenhum decorator que invoque permissao_efetiva/tem_permissao_modulo/habilitacao_efetiva/tem_habilitacao (confirmado por grep — essas 4 funções só aparecem em sua própria definição e nos 3 arquivos de teste).
Não existe context processor de permissões (config/settings/base.py lista só debug, request, auth, messages, tenant_config — este último de saas_tenants, não de accounts).
9.5 Templates
Único uso de dado de permissão em template: templates/configuracoes/index.html (variável usuario_e_admin_escritorio, 3 ocorrências — controla visibilidade de botões administrativos nessa página específica) e exibição de papel_nome (vindo de Group, não de PapelAcesso).
templates/components/sidebar.html não filtra nenhum item de menu por permissão — todos os módulos aparecem para qualquer usuário autenticado, independentemente de papel/tipo de conta.
9.6 View administrativa de permissões
apps/configuracoes/views.py::permissoes (linhas 254-317, protegida por @requer_admin_escritorio) grava dados reais em PermissaoPapel.objects.update_or_create(tipo_conta=..., modulo=..., ...) — mas exclusivamente pela via legada tipo_conta, nunca por papel=. Como nenhuma view de negócio lê PermissaoPapel, essa tela edita configuração sem efeito prático fora da própria tabela — é, na prática, um shell funcional (grava no banco, mas não influencia nenhum comportamento de acesso real).

9.7 Achado de rastreabilidade
Os arquivos test_admin_tenant.py e test_permissoes_kernel.py contêm docstrings/comentários rotulando cenários como "FALHA ESPERADA NO KERNEL ATUAL (pré-2.1C1B)" — mas, por leitura estática do código de permissoes.py/decorators.py no mesmo commit, esses cenários já deveriam passar (o próprio commit 452eeb6 afirma "62 testes, 62 OK, 0 FAIL, 0 ERROR"). Os comentários descrevem um estado de design que já estava resolvido no momento em que foram escritos — não são confiáveis como fonte de verdade sobre o estado do sistema.

11. Escopo de dados
Tabela consolidada (evidência completa por app, com arquivo:linha, no relatório do agente de apps de negócio — resumida aqui):

App	Campo de posse	Lista	Detalhe	Edição	Ação/Exclusão
clientes	responsavel	ausente	ausente	ausente	ausente
processos	responsavel + equipe	ausente	ausente	ausente	ausente
tarefas	responsavel	ausente	(sem view dedicada)	ausente	ausente
agenda	responsavel + participantes M2M	ausente (só filtra por data/status)	(sem view dedicada)	ausente	ausente

modelos	criado_por	ausente	ausente	ausente	(sem view de exclusão)
Padrão confirmado em todos os apps: o campo de posse é sempre preenchido corretamente na criação (objeto.responsavel = request.user), mas nunca é lido de volta como filtro em nenhuma operação subsequente. Isso caracteriza IDOR por design dentro do tenant, consistente e sistemático — não é uma falha pontual de um módulo, é o padrão arquitetural adotado até aqui (documentado como decisão deliberada nas Fases 2.9/2.10, ver Seção 15).

Objetos sem responsável/equipe: docs/plano-fase-2-escopo-dados.md já mapeia esse risco preventivamente ("registros com responsavel=null sumindo silenciosamente quando filtros forem ativados"), mas como nenhum filtro foi de fato ativado, essa preocupação documental ainda não tem efeito prático — todos os registros, com ou sem responsável, são visíveis a qualquer usuário autenticado hoje.

Múltiplas equipes / equipes descendentes: apps/accounts/escopo.py::equipes_descendentes existe e é recursivo, mas não é consumido por nenhuma view de negócio.

Acesso direto por ID: confirmado como o vetor primário do IDOR — todas as views de detalhe/edição/ação usam get_object_or_404(Model, pk=pk) sem cláusula adicional de posse.

Consistência entre lista/detalhe/edição/ação: a inconsistência real é que todas as quatro operações são igualmente permissivas (não há uma mais protegida que outra) — o que é ao menos consistente, ainda que inseguro.

Classificação do risco: IDOR intra-tenant sistêmico em Clientes, Processos, Tarefas, Agenda, Financeiro e Modelos. Não é IDOR entre tenants (isolamento de schema Postgres permanece intacto).

20. Dívidas e riscos
Crítico:

IDOR intra-tenant sistêmico em Clientes, Processos, Tarefas, Agenda, Financeiro, Modelos — qualquer usuário autenticado lê/edita/exclui qualquer registro de qualquer colega no mesmo tenant, incluindo dados financeiros completos do escritório. (Seção 10, 11)
Kernel de permissões sem enforcement — investimento técnico substancial (6 models, 12 migrations, 86 testes) sem nenhum efeito em produção; qualquer stakeholder que acredite que "permissões estão implementadas" (por causa dos nomes de commit "implementar kernel de papeis dinamicos") estaria enganado sobre o comportamento real do sistema. (Seção 9, 10)
DJANGO_SETTINGS_MODULE default é development em manage.py/wsgi.py/asgi.py — se a env var não for setada explicitamente no processo de produção, o deploy roda com DEBUG=True e ALLOWED_HOSTS=["*"] silenciosamente. (Seção 4, achado do agente de infraestrutura)
Alto:

Zero cobertura de teste fora de apps/accounts — os módulos com IDOR confirmado (Clientes, Processos, Financeiro etc.) não têm nenhum teste que pudesse ter capturado o problema.
Ausência de CI — nenhuma checagem automática de lint/teste/segurança acontece antes de merge (não há branches, então "antes de merge" nem se aplica — é commit direto em main).
Documentação de processo (CLAUDE.md/AGENTS.md) desalinhada com o estado real do código — risco direto para qualquer sessão futura de IA que confie nela como fonte de verdade sobre "o que não implementar ainda".
Hardening de produção incompleto — sem SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE, SECURE_HSTS_SECONDS em config/settings/production.py.
ALLOWED_HOSTS em produção depende de env var sem fallback seguro — se não setada, fica [''], bloqueando todos os hosts (falha segura, mas indica falta de validação de configuração).
Médio:

Duplicação de constantes de permissão em 4 lugares sem referência cruzada (decorators.py, permissoes_constants.py, migration 0011, configuracoes/views.py::_MODULOS_CONFIG) — risco de drift silencioso.
3 dos 5 presets de papel são dados órfãos — permanecem no banco sem caminho de atribuição via produto.
Constraint tipo_ou_papel é OR, não XOR em PermissaoPapel/HabilitacaoPapel — ambiguidade de schema não explorada pelos dados atuais, mas não impedida pelo banco.
AGENTS.md não versionado — arquivo de instruções fora do controle de versão compartilhado.
Commit 541b8be fora do padrão (formato, ausência de doc, ausência de trailer de IA) — ponto de possível revisão manual não documentada.
django-debug-toolbar instalado mas não ativado — dependência morta em requirements/development.txt.
Baixo:

Sem cache de permissões — não é um problema de segurança, mas é um ponto de atenção de performance caso o kernel venha a ser conectado a views de alto tráfego no futuro.
docs/checkpoint-fase-1.md é puramente histórico, sem ação necessária.
Ambiguidade de case-sensitivity do .gitignore (Claude.md casa com CLAUDE.md neste ambiente Windows) — sem efeito prático hoje porque o arquivo já está rastreado, mas merece nota para não confundir automações futuras.
