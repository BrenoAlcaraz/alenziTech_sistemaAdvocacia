Gestão de usuários do escritório e da sua conta
🟢 O que é
É o painel de administração do escritório: aqui o dono gerencia usuários, equipes, os dados do escritório e — o mais importante — quem pode ver e fazer o quê no sistema. Ao contratar a plataforma, o escritório recebe automaticamente 1 usuário Mestre — o dono, com acesso ilimitado a absolutamente tudo, inclusive dados de todos os outros usuários, e que nunca pode ser excluído. Por isso ele nem aparece nas telas de Permissões/Habilitações — não há nada a restringir nele. É o mestre quem cria os demais usuários (até o limite do plano), sempre com um dos 3 papéis configuráveis: Administrador, Ilimitado e Financeiro. Esses 3 têm o que podem ver e editar configurado pelo mestre, e servem de "regra geral" que todo usuário novo daquele papel segue por padrão.
🔴 Como construir
Cada usuário tem um campo papel (mestre / administrador / limitado / financeiro). O usuário mestre é criado automaticamente no fluxo de contratação/pagamento do plano (is_mestre=true), ignora toda checagem de permissão (sempre passa), e a rota/ação de excluir usuário deve bloquear explicitamente qualquer tentativa de apagar um usuário com is_mestre=true — tanto no botão do frontend (nem mostrar a lixeira pra ele) quanto no backend (retornar erro se alguém tentar via API). Para os outros 3 papéis, crie uma tabela permissoes_papel (papel, módulo, habilitado, sub_opcao) e uma habilitacoes_papel (papel, módulo, ação, habilitado) — completamente independentes entre si (editar as linhas do papel administrador nunca deve alterar as do limitado ou financeiro).

Gestão de usuários do escritório e da sua conta
🟢 O que é
Esta é a mesma tela de Configurações, só que do ponto de vista de um usuário que não é mestre — vale igual pra Administrador, Ilimitado ou Financeiro, a diferença de conteúdo aqui vem sempre das Permissões/Habilitações daquele papel, nunca do papel em si. Editar o próprio perfil, trocar senha e sair do sistema estão sempre disponíveis pra qualquer usuário. Mas o card de uso do plano (contagem de usuários, botão Novo usuário) e as opções de Administração (Equipes, Permissões, Habilitações) só aparecem se o módulo Gerir estiver permitido pra esse usuário, e mesmo assim cada pedaço específico só aparece se a habilitação correspondente também estiver ligada. Sem isso, o usuário vê uma versão bem mais enxuta: só o próprio nome (que ele pode clicar pra ver os processos em que está habilitado) e, em Equipes, só as equipes das quais ele mesmo faz parte.
🔴 Como construir
Ao carregar essa tela, consulte habilitacoes_papel (ou habilitacoes_usuario, se houver override individual) pro papel do usuário logado, checando especificamente: gerir.habilitado, gerir.criar_novo_usuario, gerir.criar_grupos, gerir.habilitar_usuarios_em_processos, gerir.habilitar_terceiros. Cada bloco da tela é renderizado condicionalmente a partir dessas flags — veja o simulador abaixo pra testar as combinações. Nunca esconda só no frontend: as rotas de API de Equipes/Permissões/Habilitações também precisam checar essas mesmas flags no backend antes de responder.
⚠️ Marque "Gerir permitido" primeiro — as 4 opções abaixo dele só têm efeito com o Gerir ligado (assim como no sistema real).
O que acontece em cada hipótese
Gerir desligado → nenhuma das 4 opções abaixo faz efeito, mesmo que estejam marcadas — ele só vê o próprio nome e "Minhas equipes".
Gerir ligado, mais nada → mesma visão enxuta de quando Gerir está desligado (o Gerir sozinho não libera nada — ele só é o "portão" pras habilitações específicas).
Gerir + Criar novo usuário → aparece o card de uso do plano completo (contagem + lista de usuários + botão Novo usuário).
Gerir + Criar grupos → "Equipes" vira gerenciamento completo (Nova equipe, Editar, Membros), em vez de só "Minhas equipes".
Gerir + Habilitar usuários em processos → aparece a linha "Permissões" em Administração.
Gerir + Habilitar terceiros → aparece a linha "Habilitações" em Administração.

Upgrade de plano
Aumente o limite de usuários e processos do seu escritório.
🟢 O que é
O sistema é vendido por assinatura mensal, com planos que limitam quantos usuários e quantos processos o escritório pode ter. Quando o escritório cresce e esbarra no limite (ex: já usou os 10 usuários do plano atual), o dono pode fazer upgrade pra um plano maior direto por aqui, sem precisar entrar em contato com o suporte — o novo limite passa a valer imediatamente após o pagamento.
🔴 Como construir
Cada plano é um registro em planos (nome, limite_usuarios, limite_processos, preco_mensal, stripe_price_id). O escritório (tenant) tem um plano_id atual. Ao clicar "Assinar", redirecione pro checkout do Stripe/Pagar.me (ou abra o formulário de troca de cartão se já tiver assinatura ativa) usando o stripe_price_id do plano escolhido. No webhook de confirmação de pagamento, atualize o plano_id do tenant. Toda checagem de limite (ex: ao tentar criar um novo usuário) deve consultar o plano atual em tempo real — nunca hardcode o número 10 em lugar nenhum do código.

🟢 O que é
Cada usuário edita os dados de exibição da própria conta: o nome que aparece pro resto do escritório, o cargo (informação descritiva, não altera o papel/permissões dele) e uma foto de perfil, que substitui as iniciais usadas hoje como avatar em todo o sistema (sidebar, listas de usuários, atividade, etc.).
🔴 Como construir
Campos nome_completo, cargo e foto_url na tabela de usuários. Upload de imagem: envie o arquivo pro storage (ex: AWS S3) num endpoint dedicado, salve só a URL retornada em foto_url. Faça resize/crop no upload (ex: 200×200) pra manter os avatars leves e consistentes. Em todo componente de avatar do sistema, troque a lógica de "iniciais do nome" por foto_url ? <img> : iniciais — mantendo as iniciais como fallback pra quem não tem foto.

🟢 O que é
Aqui o mestre vê quais processos este usuário está individualmente habilitado a acessar, e pode marcar mais processos mesmo que ele não esteja em nenhuma equipe. Isso é independente da equipe: um usuário pode estar numa equipe (que já dá acesso a um conjunto de processos) e também ter outros processos habilitados avulsamente, fora dos que a equipe dele enxerga — útil quando alguém precisa colaborar pontualmente num caso que não é da área da sua equipe.
🔴 Como construir
Tabela usuario_processos (usuario_id, processo_id) — separada de equipe_processos. Na hora de resolver quais processos um usuário com permissão "somente os seus" pode ver, combine as duas fontes: SELECT processo_id FROM equipe_processos WHERE equipe_id IN (equipes do usuário) UNION SELECT processo_id FROM usuario_processos WHERE usuario_id = usuario.id. Isso garante que o acesso do usuário é a soma do que a equipe libera com o que foi habilitado individualmente pra ele.
🟢 O que é
Esta é a visão do próprio usuário sobre si mesmo: ele está vendo quais processos ele mesmo está habilitado a acessar — os que a equipe dele já libera, mais os que foram habilitados individualmente pra ele. Diferente da tela do mestre, aqui é só consulta: um usuário comum não pode se auto-habilitar em mais processos, essa marcação continua sendo exclusiva de quem tem a habilitação "Habilitar usuário em processos" em Gerir.
🔴 Como construir
Mesma query de leitura da versão do mestre (equipe_processos UNION usuario_processos, filtrando pelo próprio usuario.id do usuário logado), mas os checkboxes e o botão "Salvar" devem ficar desabilitados/somente leitura nesta tela quando não for o mestre (ou alguém habilitado em Gerir) olhando — é uma consulta do próprio acesso, não uma ferramenta de auto-gestão.

Equipes
Organize a estrutura interna do escritório.
🟢 O que é
Equipe é um agrupamento de usuários dentro do escritório (ex: "Equipe Tributário", "Equipe Cível"). Ao criar uma equipe, o mestre escolhe exatamente quais processos e quais clientes ela tem acesso. Mas essa atribuição só funciona junto com o que está configurado em Permissões: se o papel dos membros estiver como "somente os seus", eles só vão enxergar os processos/clientes atribuídos à equipe deles; se estiver como "todos", eles enxergam tudo do escritório independente do que foi atribuído à equipe — a atribuição da equipe só passa a filtrar de fato quando a permissão está restrita.
🔴 Como construir
Tabela equipes (nome, equipe_pai_id opcional, status) + tabela de associação equipe_membros (equipe_id, usuario_id, é_gerente: bool) + equipe_processos (equipe_id, processo_id) + equipe_clientes (equipe_id, cliente_id). Na hora de resolver o que um usuário pode ver num módulo com sub_opção 'somente_seus', o filtro do backend deve ser: WHERE processo.id IN (SELECT processo_id FROM equipe_processos WHERE equipe_id IN (SELECT equipe_id FROM equipe_membros WHERE usuario_id = usuario.id)) — e se a sub_opção for 'todos', ignore esse filtro completamente.

E-mail de intimações
🟢 O que é
É o e-mail que os tribunais (como o PJe) usam pra avisar o escritório sobre novidades nos processos — intimações. Ao conectar esse e-mail aqui, o sistema passa a ler a caixa de entrada automaticamente, identifica quais mensagens são intimações judiciais, e organiza numa lista dentro do Painel — sem que o advogado precise caçar isso manualmente e correr o risco de perder um prazo por não ter visto o e-mail a tempo.
🔴 Como construir
Fluxo de conexão via OAuth do Gmail/Outlook (mais seguro que pedir senha diretamente) ou IMAP com senha de app como alternativa. Salve o token de acesso vinculado ao escritório (não ao usuário individual, já que é um e-mail institucional). Um worker em background (ex: a cada 15 min) lê a caixa de entrada, filtra e-mails com padrão de remetente/assunto de tribunal (ex: @pje.jus.br, palavras-chave como "intimação"), usa IA (ou regex pra começar) pra extrair número do processo, o que foi intimado a fazer e o prazo, e grava na tabela intimacoes (vinculando ao processo pelo número extraído). O Painel só lê essa tabela — toda a complexidade de leitura/parsing do e-mail fica contida aqui em Configurações.

Permissões
🟢 O que é
Permissão define o que cada papel pode enxergar no sistema. Desligar o interruptor de um módulo (ex: Processos) faz esse módulo inteiro sumir da tela de todo mundo com aquele papel. Cada aba de papel (Administrador/Ilimitado/Financeiro) é 100% independente das outras — mexer numa nunca afeta as demais.

O que "Somente os seus" / "Todos" quer dizer, módulo por módulo:
• Processos: "Todos" = todos os processos do escritório; "Somente os seus" = só os processos em que ele está habilitado — seja pela equipe dele, seja individualmente (na tela de cada usuário em Configurações).
• Clientes: não existe habilitação direta a um cliente. O usuário é habilitado a processos; como cada processo tem um cliente vinculado, ele só enxerga um cliente por consequência de ter acesso a pelo menos um processo daquele cliente. "Todos" = todos os clientes do escritório.
• Financeiro: "Apenas solicitações" = só o submódulo Solicitações (ele pede pagamento de custas sem ver o financeiro do escritório); "Acesso a dados" = visão financeira completa (Pagamentos).
• Tarefas: "Somente os seus" = só as tarefas dele; "Todos" = tarefas de todos os usuários.
• Modelo de peça: "Somente os seus" = só as peças que ele mesmo criou; "Todos" = peças criadas por qualquer pessoa do escritório.
• Painel e Agenda seguem a mesma lógica entre si: "Todos" = dados/agenda do escritório inteiro; "Somente os seus" = limitado aos processos e clientes que ele está autorizado a ver.
• Gerir: liga/desliga simples, sem sub-opção — controla se o usuário tem acesso à área de gerência; o que ele pode fazer lá dentro é definido em Habilitações.
🔴 Como construir
Cada linha é um registro em permissoes_papel: {papel, modulo, habilitado: bool, sub_opcao} ('somente_seus' | 'todos', ou pro Financeiro 'apenas_solicitacoes' | 'acesso_dados'). No frontend, toda rota/menu do módulo só renderiza se habilitado === true. No backend, toda query precisa aplicar o filtro de sub_opcao: 'somente_seus' filtra por equipe_processos UNION usuario_processos (ver card de Equipes); Clientes nunca tem filtro próprio — deriva de SELECT DISTINCT cliente_id FROM processos WHERE id IN (processos que o usuário pode ver). Nunca confie só em esconder no frontend — a API tem que aplicar esse mesmo filtro, senão um usuário "somente os seus" acessa dado de outro só trocando o ID na URL.

Vínculo crítico com Habilitações: se habilitado === false pra um módulo+papel aqui em Permissões, o usuário não tem NENHUMA forma de acessar as ações daquele módulo em Habilitações — não é só um efeito visual, é uma trava real de acesso. Ao renderizar a tela de Habilitações, sempre consulte primeiro esta tabela antes de mostrar qualquer toggle daquele módulo.

Gerir
Selecione um usuário para definir as permissões individuais dele.
🟢 O que é
As abas Administrador/Ilimitado/Financeiro definem a regra geral que todo usuário daquele papel segue por padrão, e que todo usuário NOVO criado com esse papel também herda automaticamente. Aqui na aba Individual, o mestre sobrescreve pontualmente só uma pessoa.

Exemplo concreto: imagine dois usuários com o mesmo papel, ambos Financeiro. Por padrão os dois seguem exatamente a regra da aba Financeiro. Se o mestre quiser que só um deles tenha uma liberdade a mais (ou a menos) que o outro, ele mexe na aba Individual daquele usuário específico — o outro usuário Financeiro continua seguindo a regra geral normalmente, sem ser afetado. E se amanhã for criado um Financeiro novo, ele nasce seguindo a regra geral da aba Financeiro, não o ajuste individual de ninguém.
🔴 Como construir
Ao criar um usuário, copie (ou apenas referencie) as permissões do papel dele como ponto de partida. Se o mestre editar algo aqui na aba Individual, grave um registro em permissoes_usuario (usuario_id, módulo, habilitado, sub_opcao) — na hora de checar permissão em qualquer lugar do sistema, consulte primeiro se existe override em permissoes_usuario para aquele usuário+módulo; se não existir, caia no padrão de permissoes_papel.

Habilitações
🟢 O que é
Se Permissão é "o que o usuário pode ver", Habilitação é "o que ele pode fazer" dentro do que já pode ver. As duas telas são umbilicalmente ligadas: se um módulo estiver desligado em Permissões para um papel (ex: Processos desligado pro Financeiro), esse grupo aparece "em fantasma" aqui, travado, com a nota "permissão desligada" — não dá nem pra ver o que poderia ser habilitado. Quando a permissão do módulo está em "somente os seus" (restrita), algumas ações de habilitação mudam de rótulo pra deixar isso explícito (ex: "Criar novo processo" vira "Apenas ver").

O que cada grupo de Habilitação libera, módulo por módulo:
• Processos: Criar novo processo, Editar processo já criado, Adicionar novo andamento. (IA ativada e Laboratório jurídico ativado são reservados para uma funcionalidade de IA futura — não fazem parte do escopo atual, só estão na tela como placeholder.)
• Clientes: Adicionar novo cliente, Editar cliente já existente, Excluir cliente.
• Tarefas: se pode criar tarefa só pra si mesmo, ou também atribuir tarefas a terceiros.
• Modelo de peça: se pode criar/adicionar um modelo novo, ou só visualizar e replicar os que já existem.
• Agenda: mesma lógica de Tarefas — anotar compromisso só pra si mesmo, ou também pra terceiros.
• Gerir (só aparece se "Gerir" estiver ligado em Permissões): Criar novo usuário, Habilitar usuário em processos, Criar grupos, e Habilitar terceiros — este último significa delegar a outra pessoa o acesso a essa própria área de Gerir, permitindo que ela também crie usuários, habilite processos e crie grupos. O mestre já tem tudo isso nativamente; aqui ele decide se estende essa capacidade de gerência pra mais alguém.
🔴 Como construir
Antes de renderizar cada grupo de Habilitações (Processos, Clientes, Tarefas...), consulte primeiro permissoes_papel pra aquele papel+módulo. Se habilitado === false, renderize o grupo colapsado/travado (só o título + "permissão desligada"), sem nem mostrar os toggles — igual já fizemos aqui no protótipo pros grupos Processos/Modelo de peças/Gerir na aba Financeiro, e Gerir na aba Ilimitado. Cada ação vira uma linha em habilitacoes_papel: {papel, modulo, acao, habilitado: bool} — ex: {papel:'administrador', modulo:'clientes', acao:'excluir', habilitado:true}. No backend, toda operação de escrita (criar, editar, excluir) precisa checar essa tabela antes de executar — de novo, nunca só no frontend.

Mesma lógica da aba Individual de Permissões: os papéis definem o padrão herdado por todo usuário novo, e aqui o mestre ajusta pontualmente as ações liberadas pra uma pessoa específica, sem mexer nas demais do mesmo papel.
🔴 Como construir
Mesmo padrão de override por usuário: habilitacoes_usuario (usuario_id, módulo, ação, habilitado) tem prioridade sobre habilitacoes_papel na hora de resolver o que aquele usuário específico pode fazer.
